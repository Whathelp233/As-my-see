# ROS 控制器与实时数据流

ROS 控制框架把控制算法与硬件通信分层：硬件适配层提供可读状态和可写命令接口，控制器声明所需接口并在周期更新中计算命令，控制器管理器协调硬件读写、控制器生命周期和接口占用。

## 1. 一次控制周期的数据流

典型闭环周期可写成：

1. 硬件层读取总线/驱动器状态，解码成带单位的关节、传感器状态；
2. 控制器管理器调用硬件读取接口，按本周期时间戳与周期时长运行激活控制器；
3. 控制器读取已声明的状态接口，使用最新参考值计算输出并写入命令接口；
4. 硬件层将命令做范围/安全检查，再编码下发到驱动器；
5. 下一周期读取新状态，闭环继续。

读、更新、写应尽可能落在可预测的周期线程里。订阅、服务、参数解析、日志和复杂内存分配通常在非实时线程处理，再把已经验证的最新值安全移交给控制循环。周期的频率由机器、驱动和负载决定；没有适用于所有 ROS 控制器的统一固定频率。

接口要回答四个问题：**什么量**（位置、速度、力矩、电流等）、**单位是什么**、**相对哪个坐标系/参考方向**、**多旧的数据算无效**。如果位置状态单位是弧度而命令按圈数解释，框架仍可能正常运行，但设备行为会完全错误。

## 2. ROS 1 ros_control

ROS 1 的 **hardware_interface::RobotHW** 为一个机器人硬件系统提供统一抽象。硬件驱动在初始化阶段建立关节状态、位置/速度/力矩命令句柄并向资源管理层注册；控制器通过命名句柄访问指定资源，避免在控制器中直接持有底层总线实现。

硬件控制线程的核心顺序是
$$
\text{RobotHW::read}\ \rightarrow\ 
\text{ControllerManager::update}\ \rightarrow\
\text{RobotHW::write}.
$$
**read** 将编码器、驱动器状态等拷贝/换算成状态接口；**update** 运行控制器；**write** 对命令限幅、转换并下发。硬件可能还有独立总线线程，此时需明确数据快照、互斥/无锁传递和时间戳，不能假设所有通信都在这一周期内同步完成。

传动层描述电机/执行器与关节量之间的映射，包括传动比与命令/状态变换。关节限位应由适当的关节限制接口或底层驱动共同保护；控制器自身的限幅不能取代硬件急停和驱动器保护。ROS 1 的具体类、注册接口与命令句柄定义以目标发行版文档为准。

## 3. ROS 2 ros2_control

ROS 2 延续“硬件、接口、控制器、管理器”的分层，但硬件组件类型、生命周期、资源拥有方式和插件 API 与 ROS 1 不同。

- **硬件组件**可按系统、执行器或传感器划分，声明要导出的状态与命令接口。
- **资源管理器**加载硬件插件并管理接口资源。
- **控制器**通过接口配置声明需要哪些 state/command interfaces；激活时管理器分配接口，避免多个控制器无意中争用同一命令资源。
- **控制器管理器**在更新周期中执行读取硬件、更新活动控制器、写入硬件的控制链，并协调生命周期。

常见控制器类继承 **ControllerInterface**，包含初始化/配置、激活、周期更新、停用等回调。更新函数接收当前时间和本周期时长，读取 state interfaces 并写 command interfaces。声明、插件导出和接口命名与发行版相关，不能将 ROS 1 的 **RobotHW**/句柄代码直接改名当成 ROS 2 实现。

一个控制器通常以插件库形式导出，由控制器管理器按配置加载。注册宏、插件 XML、包依赖和类名必须互相一致；“类能编译”还不代表插件能被管理器发现。硬件插件与控制器插件各自有基类和导出入口，不要把两类插件互换。

## 4. 非实时回调与实时 update 的边界

ROS 消息回调通常运行在 executor/spinner 的普通线程；周期更新函数则有更严格的时限要求。常见模式是订阅回调检查消息、单位和时间戳后，写入一个实时数据移交结构；周期线程每轮只取可用的最新值，缺失或过期时使用明确的保持、减速或安全停机策略。

**realtime_tools::RealtimeBuffer** 与 **RealtimePublisher** 是相关工具，但具体实现与 API 会随版本发展。应按目标发行版检查线程安全、是否可能跳过样本、调用线程与生命周期要求，不要把类名理解成绝对“无锁”或实时安全保证。

实时发布的通用目标是避免控制线程等待 ROS 发布器：若当下无法取得可用发布资源，就跳过这一帧或延后由普通线程发布。状态估计、诊断和可视化消息可有意允许采样损失；闭环命令和保护状态则需要单独设计有界延迟、超时和失效动作。消息缓冲只解决线程间数据交接，不会自动保证消息新鲜、单位正确或系统端到端实时。

实时 **update** 中避免不可控操作：动态内存分配、等待锁、磁盘/终端 I/O、阻塞服务调用、参数查询和不受限计算。也要测量代码实际执行时间及周期抖动；使用 SCHED_FIFO、线程优先级或 RT 内核不是所有控制器的默认前提，调度优先级配置错误还可能让系统其他线程饥饿。

## 5. 状态机、标定与命令看门狗

执行机构控制器通常需要显式生命周期/工作状态，例如 **UNCONFIGURED → CALIBRATING → READY → ACTIVE → FAULT**。只有在校准成功、传感器数据新鲜、限位有效且驱动器状态允许时，才允许从 READY 进入 ACTIVE。每个状态都要定义允许的命令和退出条件。

### 回零和限位校准

需要估计机械零点时，常见的受控状态序列是：

1. 用较低的速度/力矩朝限位或传感器参考点移动；
2. 以位置开关、编码器标记或有明确阈值/持续时间的驱动器反馈判定触发；
3. 退出触发区并按可验证的机械方案慢速重新接近；
4. 记录零位偏置，检查位置方向、软限位和零点重复性；
5. 若超时、读数不连续、方向不符或越界，则停止并转故障态。

不能默认把电机长时间顶住机械硬挡块作为无害的找零方式；若系统设计确需触碰机械止挡，应先确认峰值力矩、温升、夹伤和机构损伤风险，并设置硬件/软件保护。

### 命令新鲜度和状态切换

通信中断、遥操作节点退出或目标消息迟到时，控制器不应永久沿用最后命令。根据机构风险，在指定时间内无新命令便清零速度/力矩、减速至停机或进入故障态。手动开关的“按下”和“释放”是边沿事件，和持续电平语义不同；模式切换时应清除不再适用的旧目标并初始化积分器/轨迹状态，避免切换瞬间跳变。

软件看门狗不能代替硬件急停、驱动器限流、制动器和电气保护。传感器状态、驱动器状态与控制状态要分别记录，方便区分“控制器计算了什么”和“执行器实际执行了什么”。

# 性能测量、延迟与瓶颈分析

性能测试要先定义管道边界，再决定用什么时钟和统计量。一次 kernel 更快，可能被布局转换、内存复制、进程间传输、CPU 预处理或同步抵消；平均吞吐提高，也不保证每个输入的延迟降低。

## 先写清输入、输出和测量边界

开始计时前说明：输入从哪里开始可用，输出到哪里算完成，包含哪些内存分配、格式转换、传输、推理、后处理、等待和消息发布。CPU 与 GPU 版本必须有相同的输入和结果合同。

举例：

```text
端到端：CPU 已有输入 → 变换/推理 → CPU 已有同格式结果
设备段：GPU 开始执行 → GPU 完成对应计算
流水线批次：开始准备首帧 → 所有帧完成并从槽位收回
```

如果实际应用每帧申请缓冲区，就应把申请成本计入应用延迟；若为了持续吞吐预先复用资源，则应单独记录初始化成本，并明确其被摊到多少帧上。测试输入生成、校验和打印通常放在目标计时范围外，但不能在两个待比版本间只对一方排除成本。

CPU 端用单调时钟（如 C++ `std::chrono::steady_clock`）计墙钟时间。由于 kernel 启动是异步的，CPU 计时若在工作尚未完成时停止，只会测到提交时间。要测 CPU 到结果可用的延迟，结束前必须等待相关 stream/event，或观察同步返回结果的 API。

## CPU 时钟与 CUDA Event 是两种口径

CPU 墙钟计时适合衡量应用总路径，包括提交、等待、复制、CPU 处理和调度。CUDA Event 适合测指定设备队列中两点之间的时间。Event 区间已经包含在端到端区间中，不应再加一次；多 stream event 区间可能重叠，更不能简单求和。

把上传、计算和下载拆开测时，需要让每个阶段真正完成后再结束计时。可用一条 stream 记录上传前后的 event，或在 CPU 时钟的边界上等待特定阶段。过度插入同步会改变原流水线；因此“诊断分段计时”和“最终连续吞吐”应分开报告。

比较应遵循这些规则：

1. 固定输入、分辨率、迭代次数、精度、输出格式、设备功耗策略和并发负载。
2. 先预热，避免首次初始化、JIT 编译、缓存填充或自动调优只影响某个版本。
3. 重复多轮并轮换运行顺序，报告样本数、均值、中位数和高分位数；可附最大值，但最大值对样本数和偶发干扰很敏感，不应单独作为性能结论。
4. 计时前验证结果；校验与打印不混入计时。对浮点输出使用明确误差合同，对离散标签检查边界和错例。
5. 把实验构建、模型加载、引擎初始化与稳态推理分开。目标硬件上的延迟是目标，另一台设备的时间只能作参考。
6. 同时测代表性小输入和大输入。很短的任务容易被时钟读取、队列提交和同步开销主导。

数据准备、模型/引擎导出、首次加载和目标推理也应分开记录。例如某些部署工具链允许在 CPU 上导出通用计算图，再由目标设备上的运行时选择精度和构建可执行引擎；这只说明导出阶段可以不占用目标 GPU，不等于 CPU 推理时间可代表部署延迟。是否支持该路径取决于具体框架、图算子和运行时版本，见[计算机视觉与机器学习](../计算机视觉与机器学习/训练数据划分与评测.md)。

只有当各阶段按顺序互不重叠、覆盖了从起点到终点的整个计时区间时，才可以把同一样本的各阶段耗时相加得到总耗时。若阶段有并行、排队空隙或未被计时的工作，不能直接相加。不同阶段分别求出的中位数或 p95 一般也不能相加得到整体的中位数或 p95，因为各阶段慢样本未必发生在同一轮。

## 延迟、吞吐与百分位数

- **延迟**：某个输入从指定起点到结果可用的时间。需说明是否包含排队等待。
- **吞吐率**：单位时间完成的输入数，常用帧/秒或样本/秒。有限批次的 `完成数 / 批次墙钟秒数` 是该批平均产出率；若要估计稳态吞吐，应让工作足够长，或证明流水线填充和排空成本占比很小。
- **批平均产出间隔**：批次总时间除以完成数。只有在流水线足够长、填充和排空占比很小的稳态条件下，它才近似稳态产出速度；它仍不等于单帧端到端延迟。
- **p50**：一半样本不超过该值，代表中位数水平；**p95**：95% 样本不超过该值，用于观察较慢尾部。报告必须指出采用的百分位数定义和样本数。

以下独立脚本使用一组固定的教学样本演示最近秩百分位数。它不是某个 GPU 或机器人实测结果。

```python
from math import ceil, isfinite


def nearest_rank(values_ms: list[float], percentile: float) -> float:
    if not values_ms:
        raise ValueError("values_ms must not be empty")
    if not 0.0 < percentile <= 1.0:
        raise ValueError("percentile must be in (0, 1]")
    if any(not isfinite(value) or value < 0.0 for value in values_ms):
        raise ValueError("latencies must be finite and non-negative")

    ordered = sorted(values_ms)
    rank = ceil(percentile * len(ordered))
    return ordered[rank - 1]


samples_ms = [8, 8, 9, 9, 10, 10, 11, 11, 12, 12,
              13, 13, 14, 15, 16, 18, 20, 22, 25, 40]
batch_ms = sum(samples_ms)  # 教学假设：这些任务串行、互不重叠。

print(f"count={len(samples_ms)}")
print(f"mean_ms={sum(samples_ms) / len(samples_ms):.2f}")
print(f"p50_ms={nearest_rank(samples_ms, 0.50):.2f}")
print(f"p95_ms={nearest_rank(samples_ms, 0.95):.2f}")
print(f"throughput_per_s={len(samples_ms) / (batch_ms / 1000):.2f}")
```

该示例中 p50 为 12 ms，p95 为 25 ms；单个 40 ms 的长样本拉高尾部，不明显改变 p50。小样本的 p95 仍然不稳定；对真正的延迟分布应收集足够多、独立且具有代表性的样本。不同语言库的百分位数算法可能采用插值，跨工具比较前先统一定义。

## Amdahl 定律给加速预期设上限

固定问题规模时，若总运行时间中比例 $P$ 的部分可以加速 $S$ 倍，剩余部分不变，则理想总加速比为：

$$
S_{total} = \frac{1}{(1-P) + \frac{P}{S}}
$$

例如，教学假设中 80% 时间被加速 5 倍，理想总加速比也只有：

$$
\frac{1}{0.20 + 0.80/5} \approx 2.78
$$

传输、布局转换、排队和固定开销都属于未加速部分时，继续优化 kernel 的边际收益会变小。实际程序还会有同步、资源竞争和不同并行部分，公式是上界估算而非预测器。

## 用阶段计时与消融找瓶颈

先把流水线切成有清晰输入输出的阶段，例如解码、CPU 预处理、主机到设备复制、kernel、设备到主机复制、后处理和发布。阶段总时长可以指出 CPU/GPU 空转、主机预处理太慢或显存传输占主导；随后再使用 profiler 检查具体原因。

比较多个功能层级时，可以在相同输入和负载下测“生产端”“生产端加消费者”“再加下游处理”。相邻差值可帮助估计增量成本，但若新增阶段改变了缓存、排队或数据速率，差值不能解释为严格可加的模块独立成本。应重复交错各组，并核查帧率、丢帧、输出正确率、每进程 CPU、RSS、GPU 工作占比和消息接收频率。

低 CPU 使用率或低功耗读数不直接说明系统有余量，也不直接说明受功耗墙限制。需要同一时间窗口的有效吞吐、每核利用率、频率、温度轨迹、实际功耗遥测、节流计数、内存压力和磁盘/网络等待。区分“设置的功率上限”和“测到的实际功耗”；瞬时瓦数不是持续功耗曲线。若传感器或权限无法提供可信数据，应标为未测，不能从一次快照下因果结论。进程数、线程数也不等于独立占满的 CPU 核数；进程内还可能启动 OpenCV、BLAS 或数据加载线程。

把逐像素局部算子按行带并行时，带边界要补足算子依赖的 halo。连续应用多个邻域算子时，所需 halo 至少覆盖这些算子依赖半径的累积；而依赖全图统计量、连通性或全局归约的阶段不能各自独立切带后直接拼接，需保留全局阶段或增加正确的合并过程。分带改写应使用合成边界输入检查输出合同；若要求逐字节一致，不能用视觉上相似替代精确比较。只处理目标 ROI 可以减少工作量，但 ROI 外边界的候选语义必须明确，不能将测得的收益误说成通用结论。

## CPU 数据准备与 GPU 训练不要混算

离线合成、解码、增强、打包和写盘可能由 CPU 多进程执行；训练数据加载也可能由 worker 线程/进程承担；模型前向和反向则在 GPU。它们是不同管道，瓶颈与吞吐单位不同。

诊断数据构建时，分别记录计算样本/秒与写盘吞吐、每核负载、频率、上下文切换、内存/交换、磁盘 I/O 等待和实际功耗。改变 worker 数时固定输入清单、种子、缓存状态和软件版本；一个 worker 参数不会自动等于一个物理核，worker 内部可能再启动线程。以完成样本的正确吞吐和尾部时间判断，而不是只追求更高占用或功率读数。

模型的数据拆分、缓存合同和评测集职责由[计算机视觉与机器学习](../计算机视觉与机器学习/训练数据划分与评测.md)主讲。这里仅讨论运行这些管道时怎样观察 CPU/GPU 资源，不重讲训练方法。

## 进程与组件通信也有成本

同进程通信可能减少序列化或中间缓冲，但不自动等于零拷贝。是否仍复制取决于消息类型、所有权转移、发布 API 和组件实现。测量时分别观察 CPU 复制成本、峰值内存、发布/接收频率和掉帧，并对比跨进程与进程内路径的同一端到端数据合同。ROS 组件、QoS 与消息生命周期由[ROS 与软件架构](../ROS与软件架构/节点执行与组件化架构.md)主讲。

## Profiler 的分工

| 工具 | 适合回答 | 不应单独推断 |
| --- | --- | --- |
| CPU 墙钟与系统采样器 | 整体延迟、线程调度、CPU 热点和 I/O 等待 | GPU kernel 的准确设备时间 |
| CUDA Event | 指定 stream 的设备队列时间段 | 应用总延迟或多个 stream 的总时间 |
| Nsight Systems | CPU API、NVTX、GPU copy/kernel 与 stream 的时间关系 | 某个 kernel 的全部硬件瓶颈细节 |
| Nsight Compute | 单 kernel 的资源、访存和吞吐指标 | 完整应用的端到端吞吐 |

Nsight Systems 帮助定位“何时、在哪个 stream 执行”；Nsight Compute 帮助定位“这个 kernel 为什么慢”。工具会改变运行状态或插入采样开销，最终成绩应使用适合测量目标的普通运行重复确认。

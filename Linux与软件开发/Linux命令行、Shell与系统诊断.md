# Linux 命令行、Shell 与系统诊断

终端把人输入的文本交给 Shell 解析，再由 Shell 把参数、环境、标准输入输出和进程控制传给程序。掌握解析顺序与输出流，能把许多零散命令组合成可重复的检查步骤；排障时则要把“观察到什么”与“猜测原因”分开。

## Shell 如何处理命令

Bash 会识别引号和运算符、展开变量与命令替换、做分词与通配符扩展，再执行命令。变量内容如果不加引号，空格和通配符可能把一个值拆成多个参数：

```bash
name="sensor logs"
printf '%s\n' "$name"
printf '%s\n' "$@"     # 每个脚本参数保留为独立参数
```

单引号保留字面内容；双引号仍允许变量和命令替换；反斜杠可保护后一个特殊字符。命令替换使用 `$(command)`。不要把不可信文本交给 `eval`：它会再解析字符串为 Shell 语法。

赋值号两侧不能有空格，例如 `limit=10`。脚本通常用 shebang 指定解释器，位置参数通过 `$1`、`${10}` 访问，参数个数用 `$#`，程序名用 `$0`，状态码用 `$?`。循环参数时通常使用 `"$@"`；`"$*"` 会把所有参数合成一个字符串，语义不同。

退出码 `0` 表示成功，非零表示失败；具体含义由程序定义。管道默认使用最后一个命令的状态。Bash 的 `set -o pipefail` 会让管道中失败的命令影响整个管道状态，但仍需按脚本逻辑检查和处理错误。不要把 `set -e` 当成完整错误处理机制，它在条件表达式、函数和复合命令中有需要逐条理解的例外。

## 标准输入、输出与管道

- 标准输入（stdin）默认来自终端或重定向输入。
- 标准输出（stdout）用于正常结果。
- 标准错误（stderr）用于诊断信息。
- `|` 把左侧命令的标准输出接到右侧命令的标准输入。
- `>` 覆盖文件，`>>` 追加文件；这两种重定向都会改变文件。

以下命令仅作**只读观察示例**，展示如何按字面字符串筛选、排序并统计重复的完整行；运行时仍需检查输入文件和输出路径：

```bash
grep -F "timeout" application.log | sort | uniq -c
journalctl -b -p warning
```

一些常用文本工具的语义容易混淆：

| 工具 | 作用 | 注意 |
| --- | --- | --- |
| `grep` | 按模式筛选行 | 默认模式是正则表达式；要查字面字符串时使用固定字符串模式 |
| `cut` | 按分隔符/字段或字符位置切割 | 适合固定格式；对引号内含分隔符的 CSV 不够可靠 |
| `tr` | 逐字符替换、压缩或删除 | 不能按字段理解结构化数据 |
| `sort` | 按行排序 | 默认按文本排序；数字排序要使用相应选项 |
| `uniq` | 只处理相邻的重复行 | 统计全体重复值前通常先排序，或使用专门的数据处理工具 |
| `tee` | 同时复制标准输入到终端与文件 | 默认覆盖文件，追加需明确选择 |
| `paste` | 按行并列合并多个输入 | 各文件行数不同时会补空字段 |
| `xargs` | 把输入解析成命令参数并执行命令 | 空格、引号和换行会影响拆分；处理文件名优先使用 NUL 分隔，并确认目标命令安全 |

管道传的是字节流，和把前一个命令的输出作为后一个命令的某个特定参数不同。若要批处理带空格、换行或前导连字符的文件名，应采用能保留文件名边界的 NUL 分隔输入，并让接收命令以 `--` 终止选项解析。批量删除、覆盖或改名命令要先对小样本预览，再明确确认路径范围。

## 硬链接与符号链接

目录项把名称关联到文件系统对象。硬链接是在同一文件系统中为同一 inode 增加另一个目录项；通过其中一个名字修改文件内容，其他名字看到的是同一对象。通常不能给目录创建硬链接，也不能跨文件系统建立硬链接。删除一个名字只移除对应目录项；只要仍有其他硬链接或进程打开该文件，数据就可能继续存在。

符号链接是包含目标路径的独立文件系统对象。它可以跨文件系统，也可以指向目录；目标被移动或删除后，链接会悬空。相对目标按符号链接所在目录解释。两者都不是“复制文件”，也不等于进程可直接访问的内存指针。`ln` 默认创建硬链接，`ln -s` 创建符号链接；执行前要确认源和目标路径，避免名字冲突。

## 写可维护的 Shell 脚本

把重复命令放进脚本前，先明确输入参数、工作目录、预期输出、错误退出码和是否会修改系统。建议：

1. 使用引号保护变量展开；路径变量传给命令时尤其如此。
2. 对必填参数、文件是否存在和权限做显式检查。
3. 对关键命令检查退出码，并把诊断写到 stderr。
4. 输出日志时使用时间、阶段和对象标识；避免把密码、令牌或私钥写进日志。
5. 对长任务设置明确的超时、取消和退出清理策略；脚本无法代替应用内部的并发所有权设计。
6. 先用解释器的语法检查或跟踪模式检查脚本，再在隔离目录和非生产目标上验证。

设环境变量可让子进程继承配置，但变量只是一份字符串，不会替代对路径、版本和取值范围的校验。把长期环境配置写入 Shell 启动文件会影响之后启动的交互 Shell；修改前记录原值，修改后开新 Shell 验证。

## SSH 与远程主机

SSH 客户端连接由“用户、主机名或地址、端口和认证方式”组成。密钥认证分为私钥与公钥：私钥留在客户端并限制访问权限，公钥配置到服务器允许的账户。首次连接时，客户端还会记录服务器主机密钥；若已记录的主机密钥突然变化，先通过可信渠道确认主机身份，不要为了绕过提示而清空全部信任记录。

以下是**需要用户主动执行的远端访问示例**，会发起网络连接：

```bash
ssh user@host.example
```

连接失败时分别检查 DNS/路由、TCP 端口可达性、服务器是否运行 SSH 服务、账户权限、客户端私钥与服务器主机密钥。不要把“能 ping 通”当作 SSH 一定可用的证明；ICMP 与 SSH 是不同协议。

## 日志与系统状态的只读检查

常用只读观察命令包括：

```bash
journalctl -b -p warning --since "2026-11-16 09:00:00"
systemd-analyze time
systemd-analyze blame
ip address
ss -ltn
top
```

`journalctl` 可按启动记录、时间范围、服务名或优先级筛选系统日志。优先级从 0（紧急）到 7（调试）；指定一个级别通常会同时显示更严重的级别。时间戳必须与被诊断系统的时区和时钟同步状态对应。`systemd-analyze blame` 展示服务启动耗时排序，但慢启动可能是等待前置服务的结果，它本身不证明某服务是根因。`top`、`free`、传感器监控工具和硬件信息工具适合检查资源状态，部分硬件信息查询可能需要提升权限。

设备网络、进程日志、驱动加载与时间同步都是独立故障域。修改网卡配置、安装驱动、切换内核、停用时间同步、修改服务或设置自启动都可能改变系统状态；先收集当前配置与日志，再查对应发行版、内核和设备的官方说明，不要把某台机器的修复命令复制为普遍步骤。

## 把故障定位变成证据链

出现异常时，先记录可复现的现象，再提出可证伪的假设。沿数据路径分别记录输入、接受、处理、输出和落盘计数，确认缺失最早出现在哪一段。组件内部的“丢弃计数”通常只覆盖组件已接收之后的丢弃，不足以说明设备、网络或上游队列没有丢数据。

按如下顺序缩小故障范围：

1. 固定版本、主机、时间范围、输入和启动方式，保留原始日志。
2. 把端到端耗时拆成启动、输入等待、计算、通信和输出；区分均值、分位数、最大值与样本数。
3. 做一次只改变单一变量的对照；如果改变参数后现象未变化，就降低相关假设的可信度。
4. 对构建错误分层：配置阶段查依赖发现；编译阶段查头文件和语言标准；链接阶段查目标与库；运行阶段查加载路径、环境变量、权限和动态依赖。
5. 修复后用同一输入与条件复验，并说明结论能证明什么、不能证明什么。

一个有效的诊断报告至少包括：现象和复现步骤、预期与实际、环境/版本、时间戳、原始错误、数据流计数、已排除假设、采取的最小改动、验证结果和剩余不确定性。一次“成功启动”或一次相似的输出值不能证明整条链路正确。

## CSV、YAML 与结构化数据

CSV 是带转义和引号规则的记录格式，字段可能包含逗号、引号或换行；用 `cut` 按逗号拆列会误解析这类数据。Python 标准库的 `csv` 模块可以按 CSV 规则读取，处理时要明确编码、分隔符和表头。Excel 的 `.xls`/`.xlsx` 是不同格式，通常需要相应第三方库，不能按普通文本处理。

YAML 映射对应键值关系，序列对应有序列表；块格式和紧凑格式可表达相同结构。读取配置时应检查字段是否存在、类型是否正确、单位和范围是否合理，再把解析值转换成程序内部类型。不要只因某个键能被转换就认为整份配置有效。需要原子应用运行期配置时，应一次验证完整配置并交换一致快照，而不是让并发调用方看到部分更新。

ROS 参数 API 与发行版有关；ROS 参数、消息和节点的主讲内容见 [ROS 与软件架构](../ROS与软件架构/节点执行与组件化架构.md)。本节不把旧版 ROS 1 `XmlRpcValue` 示例当作 ROS 2 写法。

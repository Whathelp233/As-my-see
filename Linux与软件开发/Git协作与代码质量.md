# Git 协作与代码质量

Git 用对象和引用记录内容及其历史。常见工作流程可以理解为三个位置：工作区保存当前文件，暂存区记录下一次提交的快照，提交历史保存已经创建的版本。`git status` 显示三者之间的差异；`git diff` 查看尚未暂存的内容，`git diff --staged` 查看已暂存但未提交的内容。

## 一次可审查的改动

下面是**工作流程示意**，需要在目标仓库确认分支和文件后再执行；`add`、`commit`、`push` 会改变本地或远端状态：

```bash
git status --short
git diff
git diff --check
git add path/to/related-files
git diff --staged
git commit -m "fix: handle partial reads"
git push origin feature/partial-read
```

一次提交聚焦一件事，提交前检查暂存区，避免把编辑器临时文件、构建产物、密钥或无关文件一起提交。提交信息说明改动意图，不应代替代码评审。团队可采用 Conventional Commits 等约定，但前缀含义应由项目统一定义。

## 分支与远端跟踪

分支是指向提交的可移动引用。创建分支后，提交只推进当前分支；基线分支上的新提交不会自动出现在你的分支上。`git fetch` 更新远端跟踪引用但不合并到当前工作区；`git pull` 通常由 fetch 加合并或变基组成，实际方式可能受配置和命令参数影响。提交自己的分支前，先确认本地分支、上游跟踪分支和目标远端一致。

远端跟踪分支如 `origin/main` 是远端状态的本地记录，不是实时网络查询。切换或比较分支前，查看远端、最近提交和工作区状态。对共享分支改写历史会影响其他协作者；团队协作应遵循仓库约定，优先使用可审查、可回滚的提交。

## 合并冲突和回退

冲突表示 Git 无法自动合并同一文件中的修改。先查看冲突标记和各分支变更意图，再逐段解决；删除冲突标记后检查整个文件，运行相关验证，并确认暂存区只包含预期结果。不要简单选择“当前”或“传入”一侧而忽略语义。

`git revert` 创建一个反向提交，适合在共享历史上撤销已提交的变更；`git reset` 会移动当前引用并可能改变暂存区或工作区内容，尤其 `--hard` 会丢弃未提交修改。执行任何重置或清理操作前先检查 `git status`、保留需要的改动并读清命令影响范围。`git restore` 也会覆盖指定文件的本地内容，必须先确认目标路径和内容可丢弃。

## 忽略规则与仓库清洁

`.gitignore` 用于让尚未跟踪的文件保持未跟踪，例如构建目录、编辑器缓存和本地临时配置。忽略规则不会自动取消已经跟踪的文件；遇到意外提交，应检查索引状态并按团队流程处理。规则支持路径模式，子目录 `.gitignore` 可补充或覆盖上层规则。共享忽略规则放在仓库，个人机器特有规则可放在本地 exclude 文件中。

对日志、配置和生成物逐项检查敏感信息。不要把访问令牌、私钥、账户密码、私有地址或设备序列号放进 Git；删除历史中的文件也不一定让旧提交中的内容消失。若凭据泄露，应立即通过对应服务撤销或轮换，不能只靠新提交删除文件。

## 代码评审与验证

评审应围绕行为、边界和失败路径，而不是只看格式。检查输入范围、空值、单位、错误处理、资源所有权、线程安全、可移植性、性能与可观测性；再确认修改是否有测试、文档和回滚方式。对硬件或特定发行版行为，记录环境与版本，不把某台机器的结果泛化为平台保证。

验证命令应覆盖改动实际影响的层级：格式和静态检查、单元测试、构建、集成或端到端场景。测试失败要保留完整命令、退出状态和摘要；只报告“成功”会丢掉复核所需的信息。开发规范、构建环境和测试要求应遵循目标仓库自身的约定，通用示例不能替代项目说明。

Git hook 可在提交或推送等操作前后运行本地检查，例如格式或快速测试；它是本地便利机制，可能未安装、被绕过或依赖不同环境，不能代替持续集成和评审。仓库应记录如何启用 hook，并让同一项关键验证也能在标准构建环境重复运行。

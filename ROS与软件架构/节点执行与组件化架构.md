# 节点执行与组件化架构

ROS 图描述节点和接口间的连接，但不能单独说明软件层次、线程、资源所有权或“何时可以安全工作”。本篇从包到回调解释运行结构，并把 ROS 1 与 ROS 2 的机制分开说明。

## 1. 包、进程与节点

- **包**是构建和分发边界，管理依赖、接口、可执行文件、插件元数据和启动配置。ROS 1 常见 catkin + `package.xml`/`CMakeLists.txt`；ROS 2 常见 ament。包不等于进程。
- **进程**提供地址空间、故障隔离和操作系统资源。一个进程可以只运行一个节点，也可以运行若干可组合节点。
- **节点**持有 ROS 名称、参数、通信端点和回调。节点是逻辑边界；它是否与其他节点共享进程，需由部署方式决定。
- **接口包**集中定义 `.msg`、`.srv`、`.action`（具体文件类型和生成方式依 ROS 版本而定），使实现方和使用方共享类型与语义。

常见分层为：硬件驱动/仿真适配器 → 设备状态与基础接口 → 算法/控制能力 → 任务编排与系统监督 → 可视化和运维工具。依赖方向应尽量向稳定、低层的接口汇聚。高层任务不应直接依赖设备寄存器，算法插件也不应私自拥有整套系统的启停权。数值算法、信号处理、状态估计、坐标变换、传感器总线与控制律分别由相邻专门模块主讲；本层重点是把这些能力封装成边界明确、可观察的组件。

节点切分常以“独立变化、资源/故障边界、更新频率和测试方式”为依据。切得过粗会把无关功能绑在同一进程和生命周期；切得过细会增添序列化、配置、发现和运维成本。高频控制环通常需要边界明确、可预测的执行路径，低频编排和界面更新可用更松耦合的接口。

## 2. 命名空间、参数与配置

完全限定名称由命名空间和资源名称组成。命名空间可区分机器人实例、传感器或功能域；remap 用于部署时把逻辑接口接到实际名称。写接口时应定义默认名称、命名空间规则以及允许 remap 的范围，避免组件依赖某个机器人的全局绝对路径。

### ROS 1

ROS 1 参数通常经由中心参数服务器访问。节点句柄影响相对名称解析，`~name` 是节点私有参数，`/name` 是绝对名称。launch/XML/YAML 常用于组合命名空间、参数和 remap。老工程中的 `dynamic_reconfigure` 定义可在线修改参数和回调，但这是 ROS 1 机制；它不应被写成 ROS 2 API。

### ROS 2

ROS 2 参数属于单个节点，不存在 ROS 1 式的全局参数服务器。可在启动时通过 YAML 或 launch 参数注入，也可通过参数服务在运行期修改。节点要显式声明参数，并用校验规则约束类型、范围、只读性和参数联动。如果一次配置必须整体生效，需使用该发行版提供的原子参数设置机制；逐个设置参数可能出现中间状态。参数回调应短小、可失败并在失败时保持旧配置，不应在回调里做长时间 I/O 或阻塞执行器。

适合参数的内容包括阈值、频率、有限个运行模式和设备配置；频繁数据流、任务目标和需要反馈/取消的操作应走 topic/action 等接口，而非把参数当消息通道。

## 3. Launch 与就绪性

Launch 文件描述要启动的进程、节点/组件、参数、命名空间、remap、环境和退出关系。ROS 1 launch（XML 为主）与 ROS 2 launch（Python 为主，也支持 XML/YAML）语法和能力不同。Launch 文件中的“声明一个启动动作”只表明编排器计划启动它；进程创建成功、ROS 图发现完成、服务可用、参数加载成功、生命周期进入 Active 是不同层级的事实。

因此启动顺序不能仅靠文件中的先后位置保证。依赖节点应明确 readiness 条件，例如：

1. 进程已存活；
2. 必需接口已创建且类型/QoS 匹配；
3. 资源配置成功；
4. 设备或模拟器报告可用；
5. 管理型节点已切到允许处理业务数据的状态；
6. 系统监督器确认关键输出有效且数据不过期。

若其中任何一步失败，应停止上层任务或进入预先定义的安全降级，而不是仅因为进程还在就报告“系统就绪”。重启策略应限制重启频率并留下故障原因，避免无穷快速 respawn。

## 4. ROS 2 执行器与回调组

ROS 2 执行器（executor）从订阅、服务、定时器、动作等实体取出可执行回调。单线程执行器在一个线程逐个执行；多线程执行器提供并发机会，但某回调是否并行，仍受 callback group 约束。默认 callback group 通常是互斥组；可重入组允许同一组回调重入执行，因此共享状态需要自行保护。

并发不是自动的性能提升。回调需要明确线程安全、最长工作量和资源所有权：

- 回调中做少量校验、更新状态或投递任务；大块计算放入有界工作线程/任务队列。
- 多个回调共享的对象应由单一所有者、锁、不可变快照或消息传递保护。
- 不要在单线程 executor 的回调里同步等待另一个必须由同一 executor 执行的服务/未来结果；互斥 callback group 中也可能出现同类死锁。
- 多线程 executor 不保证回调顺序。若需要序列化状态修改，使用互斥 callback group 或单消费者队列，并明示队列策略。
- 线程池/队列要有容量、超时、取消和关闭策略，防止输入快于处理而无限占用内存。

ROS 1 `roscpp` 有 callback queue 和 spinner 等机制，名字与 ROS 2 executor 不同。ROS 1 的 `AsyncSpinner` 也不会自动使业务对象线程安全。选择 ROS 版本后，应根据该版本 API 阅读相应执行机制，不能将 ROS 1 spinner 代码贴进 ROS 2 节点。

### 时间、定时器与日志

ROS 时间可以跟随系统时钟，也可以在仿真/回放时跟随 ROS clock。涉及仿真时，应在统一时钟源下计算数据年龄和超时；墙上时钟、单调时钟与 ROS 时间不能无条件混算。ROS 1 中 `ros::Time`、`ros::Duration`、`ros::Rate` 和 ROS 计时器各有不同职责：`Time` 表示时间点，`Duration` 表示间隔，`Rate` 用于循环频率节拍，计时器把周期回调交给 ROS 调度。ROS 2 对应使用节点 clock、Duration、Rate/Timer 等 `rclcpp` API，且时间源受节点 `use_sim_time` 等配置影响；类名相似不代表跨版本可直接替换。

周期回调只应做有界工作，不应把 `sleep` 或同步服务等待塞进高频回调。调度周期不是硬实时保证：回调耗时过长会造成延迟，计时器也可能出现跳过或延后。需要验证实际频率时，应测时间戳和回调耗时，而不是依据设定参数推断。

ROS 日志按 DEBUG/INFO/WARN/ERROR/FATAL 等级表达诊断严重性；高频路径应使用限频/节流或聚合，避免磁盘输出造成背压。ROS 1 与 ROS 2 的日志宏、命名和配置接口版本不同，示例要标清 API。进程、文件描述符与设备文件的通用知识见[Linux 与软件开发](../Linux与软件开发/POSIX文件IO、设备控制与套接字.md)，GUI 日志窗口和跨线程刷新见[Qt 与界面开发](../Qt与界面开发/Qt对象模型、信号槽与线程.md)。

## 5. 组件、插件与名称区分

**组件（component）**把节点实现装入可管理的进程/容器，由容器负责加载和执行。ROS 1 nodelet 与 ROS 2 composable node 都支持进程内组合，但接口、构建和加载 API 不同。进程内通信可减少序列化或拷贝开销；是否真正零拷贝还取决于消息类型、内存策略、RMW 和具体配置。组件共享进程也意味着崩溃、内存泄漏和线程资源可能相互影响。

**插件（plugin）**让框架在运行时依据稳定基类加载可替换实现。使用 pluginlib 一类机制时，要把提供位置、三种插件标识和基类契约分清：

1. **提供包/共享库**：实现被编译、导出和安装的位置；
2. **lookup alias**：插件注册 XML 中 `<class name="...">` 的查找别名，框架配置通常用它请求加载；
3. **C++ 实现类型**：XML 中 `type="..."` 所指的真实类型，应继承或实现声明的基类；
4. **基类契约**：XML 中 `base_class_type="..."` 与宿主框架期望的抽象接口；
5. **配置实例名**：运行配置中的插件槽位名，供参数命名、日志和资源归属使用。它不一定等于 lookup alias。

例如规划器插件配置中的槽位名 `GridPlanner`、lookup alias `planner_plugins/GridPlanner` 和 C++ type `planner_plugins::GridPlanner` 是三个不同标识。排错时分别核对插件 XML 的库路径、lookup alias、实现类型和基类、共享库是否安装、配置实例是否指向该 alias、依赖是否可加载。只改配置字符串不能替代插件导出和构建。

下列 ROS 2 pluginlib 注册形状仅用于说明命名关系，不是完整可编译插件：

```xml
<library path="polygon_plugins">
  <class name="polygon_plugins/RegularPolygon"
         type="polygon_plugins::RegularPolygon"
         base_class_type="polygon_base::RegularPolygon">
    <description>多边形实现</description>
  </class>
</library>
```

配置中的插件值使用注册 alias `polygon_plugins/RegularPolygon`；宿主的插件槽位名另由该宿主的参数结构决定。

插件适合策略、驱动或算法实现需要可替换，而调用方可依赖稳定抽象的地方。插件边界应规定资源所有权、初始化/清理方法、线程模型、错误返回和版本兼容；不要让插件绕过宿主框架直接修改全局状态。

## 6. 监控与可观测性

系统需要区分进程存活、节点发现、接口连接、数据新鲜、功能就绪和任务成功。每一层使用单独健康信号，并由监督器组合判断。日志应包含时间、节点、任务/请求标识、状态变化和错误码；频繁循环日志需限频或聚合，防止 I/O 反过来拖慢执行回调。

话题存在并不代表数据有效；服务可连接并不代表设备可执行；进程无崩溃也不代表任务进展。给关键任务设置开始、反馈、终态和超时记录，与通信文章中的接口字段约定一致。

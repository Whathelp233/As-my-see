# 软件模块与异步任务

机器人任务通常跨越多个节点、设备和较长时间。架构必须回答：谁拥有任务、谁可以并发修改状态、异常怎么传播、取消是否真正停止，以及系统退出时如何让资源安全收尾。

## 1. 模块边界与所有权

一个模块应有单一、可描述的职责；它通过类型化接口暴露输入、输出和错误语义，并封装内部线程、设备句柄和临时状态。将“实现对象”和“拥有对象”的关系写清楚：

- 硬件驱动拥有设备句柄、读写缓存和驱动线程；上层不直接释放或重置这些资源。
- 任务服务器拥有被接受的目标、反馈节奏、终态和取消流程；调用方只持有目标句柄/结果，不可假设异步请求会自动取消。
- 状态管理器是状态转换的唯一写入者，其他模块发送事件或请求；不要让多个回调都可直接切换全局模式。
- 配置在初始化/配置阶段集中验证。运行期修改要么经过单一协调器并形成一致快照，要么拒绝有互相依赖的部分更新。

边界应允许模块独立测试：为设备、时钟、外部服务、执行器和日志接口提供替身；测试状态转换、错误、超时和取消，不把“能启动节点”当作完整验证。

## 2. 同步调用与 Future

同步调用方便但会占用调用线程，并让调用者与服务端耗时、回调线程模型和失败方式紧耦合。异步 Future 让调用者先返回，结果稍后通过轮询、回调或等待获取；它本身不代表服务端会在指定时间完成，也不自动带有取消能力。

正确管理异步调用需要回答：

1. Future/请求状态由谁持有到完成？对象销毁时如何断开回调？
2. 等待是否有上限？超时后只停止等待，还是向服务端发取消/撤销？
3. 回调在哪个 executor/线程执行？它能否安全访问对象？
4. 重试是否可能造成操作重复？调用是否幂等，是否带 request ID？
5. 结果晚于新目标返回时，如何防止旧结果覆盖新状态？

对长耗时任务使用 Action/目标句柄，并在客户端保存目标代次或 ID。新目标接管时，先对旧目标执行定义清楚的取消/抢占流程；收到迟到的结果时，验证它仍属于当前代次。不要在回调里无限等待 Future，也不要在对象析构后让捕获了裸 `this` 的异步回调继续访问已销毁对象。优先用明确的 shared ownership、weak reference、取消令牌或由生命周期持有的任务对象。

ROS 2 `rclcpp` 中可以使用异步服务客户端和 Action 客户端的 future；ROS 1 的 `roscpp`、`actionlib` 使用其他类型和回调模型。具体 API 依发行版而变，因此这里描述所有权和调度原则，不混写两个版本代码。

## 3. 单消费者任务队列

当若干生产者发出任务，而设备/控制器要求串行操作时，可以由单个消费者拥有执行状态。队列中保存经过校验的任务值，而非指向生产者临时对象的悬空引用。一个任务至少要有类型、输入快照、request ID、创建时间/截止时间、取消状态和完成结果。

先根据语义选队列策略：

| 策略 | 行为 | 适用语义 | 风险 |
| --- | --- | --- | --- |
| 有界 FIFO | 按序处理，满时拒绝或返回过载错误 | 不可合并的短任务 | 需定义满队列时的调用响应和公平性 |
| 最新值覆盖 | 用新任务替换尚未执行的旧命令 | 目标/设定值只看最新值 | 不能用于“每项都必须完成”的业务操作 |
| 同类合并 | 对相邻、等价请求合并 | 可幂等且只关心最终目标的配置变更 | 合并条件必须可证明，不可凭字符串猜测 |
| 优先级/截止期 | 按重要性或时间预算调度 | 有明确紧急级别的任务 | 饥饿和优先级反转需监控 |

消费循环的推荐语义：取出任务 → 检查取消和截止期 → 验证前置状态 → 执行有界步骤/等待异步结果 → 发布进度 → 以唯一终态完成 → 释放资源。若执行期间发生故障，要说明任务是否部分生效、设备当前状态如何、能否重试。队列关闭时停止接收新任务，取消或完成正在处理项，再按合同排空或丢弃余项；不能让消费者在队列对象销毁后继续工作。

一个小型单消费者队列与 ROS callback executor 是不同层次：executor 调度 ROS 回调，业务队列控制业务任务的串行/覆盖/优先级策略。不要用“多线程 spinner/executor”代替业务并发设计。

## 4. 超时、重试与错误边界

超时是调用方对等待时间的限制，不保证远端动作已停止。超时后的策略要区分：请求未发送、结果未知、执行中待取消、已经执行但响应丢失。对有副作用的调用应通过 request ID 查询结果，或使用幂等键避免重试重复执行。

重试可用于明确的暂时性故障，并应有上限、退避和抖动；输入无效、权限拒绝或状态冲突通常不因重试消失。错误向上层传播时保留类别和上下文，不把所有错误压成 `false`。内部实现细节、堆栈和设备返回码应映射为稳定的公开故障类别；详细诊断放日志中，并包含请求 ID/节点/任务阶段。

## 5. 日志背压与观测

日志是 I/O，可能阻塞线程或形成大量数据。高频回调避免逐样本同步写盘；改用限频、计数汇总、采样、异步日志或环形缓冲，并明确容量与溢出策略。对安全事件不能静默丢弃，应保证关键故障被记录或单独升高告警。

至少记录：任务/请求 ID、输入是否接受、阶段转换、关键时间戳、超时/取消原因、错误类别、队列长度或拒绝计数、数据是否过期。记录时避免传感器原始流全部写日志；数据流应走专门记录工具和有容量预算的存储。

当异步日志缓冲区满时，设计者需选择并记录：阻塞生产者、丢弃低优先级、覆盖旧调试日志、采样，或提升背压告警。实时控制回调通常不能因普通日志无限阻塞，但安全停机和设备故障信息需要另有可追溯路径。日志队列、通信队列、业务任务队列是三个独立容量，需要分别观测。

## 6. 停止与析构顺序

有序退出是资源所有权的反向过程。若系统依赖关系是监督器 → 任务编排 → 算法/控制器 → 硬件驱动，则通常先让上层停止产生任务，再让下游停止/安全收敛，最后释放设备、线程和进程资源。具体顺序需按依赖和安全需求设计，不能仅依赖进程被杀后操作系统自动清理。

推荐收尾步骤：

1. 停止接收新目标和配置更新，明确拒绝正在到达的请求。
2. 取消/停止活动任务；对执行器发受控停止或进入安全输出，等待有界确认。
3. 停止定时器和业务生产者，使其不再向队列添加工作。
4. 关闭队列并唤醒消费者；依约排空、取消或记录未完成任务。
5. 等待工作线程退出（join），确保没有回调再访问即将销毁的对象。
6. 停止 ROS 执行器/回调处理，关闭发布端和服务端，再释放硬件与内存资源。
7. 最后刷新关键日志/状态记录，给监督器返回最终退出原因。

真实顺序可能要求先禁用驱动写入，再将控制器切到 inactive，或由安全控制器接管。关键是显式说明谁拥有“最后一次写命令”的权力，并验证停止请求与程序退出之间不会留有无限期旧命令。
